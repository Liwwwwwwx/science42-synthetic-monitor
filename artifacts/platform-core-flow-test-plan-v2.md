# Science42 平台核心流程自动化测试计划（第二条专项）

## 1. 文档定位

本计划针对老板新方案中的第二项目“平台核心流程监控目标”制定：

> 对平台登录、消息发送、流式回答及结果返回进行自动化测试，及时发现登录失败、发送无响应、回答超时、页面一直“生成中”等问题。

本专项不是简单验证“能否问出一个答案”，而是验证一次真实业务链路从登录、进入聊天页、创建/恢复会话、发送消息、接收流式增量、生成结束、内容完整性、结果保存到刷新恢复的全过程，并在异常时留存证据、触发告警和完成复测闭环。

## 2. 测试目标

### 2.1 功能目标

1. 验证账号登录成功、登录失败、会话失效和重新登录流程。
2. 验证新建任务/新建会话、进入聊天页、发送按钮和输入框状态。
3. 验证消息确实提交，避免出现点击后无请求、重复提交或消息未入会话。
4. 验证流式回答持续产生增量内容，而不是只检查最终页面文字。
5. 验证回答最终结束，页面不长期停留在“生成中”。
6. 验证返回内容非空、未被截断、顺序正确，并与问题关联正确。
7. 验证会话保存、刷新、重新打开后，用户问题和助手结果仍可恢复。
8. 验证连续请求、同一会话多轮请求、并发请求和长文本请求下的稳定性。

### 2.2 监控目标

- 发现登录失败、验证码/登录态失效、页面跳转异常。
- 发现发送无响应、接口不发起、请求失败、重复发送。
- 发现首个流式片段迟迟不返回、流式中断、增量内容不连续。
- 发现超过阈值仍处于“生成中”、按钮状态不恢复、页面卡死。
- 发现返回空内容、半截内容、错误内容、角色错位或结果未保存。
- 发现刷新/恢复后历史消息缺失、顺序变化或恢复到错误会话。

## 3. 测试范围

### 3.1 范围内

| 模块 | 检查内容 |
|---|---|
| 登录 | 登录页加载、账号密码提交、登录成功跳转、错误提示、登录态保存与失效恢复 |
| 聊天入口 | `/chat` 可访问、聊天输入框可用、新建任务/新建会话可用 |
| 消息发送 | 文本输入、发送按钮、回车发送、请求发起、用户消息入列表、重复点击防护 |
| 流式回答 | 首包时间、增量片段数量、片段间隔、连接关闭、最终内容合并 |
| 结果返回 | 非空、完整、角色正确、格式符合要求、结束状态明确 |
| 会话 | 多轮上下文、保存、刷新、历史会话重新打开、消息顺序和内容一致 |
| 异常监控 | 超时、5xx/504、网络中断、空响应、长时间生成、前端错误、重试与告警 |
| 证据留存 | 请求时间、URL、状态码、耗时、页面截图、Trace、原始响应、运行摘要 |

### 3.2 本阶段不纳入

服务器 CPU、内存、磁盘、服务进程和代理健康检查属于第一项目；团队功能及团队接口属于第三项目。本计划只定义与平台核心聊天链路相关的浏览器和接口观测点，但会保留接口请求信息供第三项目复用。

## 5. 测试数据设计

测试数据分为基础功能、流式特征、边界异常和会话恢复四组，避免只使用简单算术题。

### 5.1 基础功能数据

| 类型 | 示例 | 校验重点 |
|---|---|---|
| 精确计算 | `请计算 987654321 × 123456789，并只输出整数结果。` | 结果正确、无多余解释 |
| 知识问答 | `用两句话解释什么是 HTTP 504，并说明它与客户端超时的区别。` | 内容非空、关键词存在、句数约束 |
| 结构化输出 | `请严格只输出 JSON：{"name":"Zhang San","age":18}` | 可解析 JSON、字段和值正确、无 Markdown 包裹 |
| 列表输出 | `请用三点列出：测试、记录、复盘。` | 恰好 3 点、顺序和关键词正确 |
| 长文本 | 发送不少于 2,000 字的中文测试材料并要求提取 10 个要点 | 长输入不丢失、不报错、返回完整 |
| 多轮上下文 | 第一轮定义变量，第二轮引用变量并计算，第三轮要求总结 | 上下文保持、角色和顺序正确 |

### 5.2 流式回答数据

至少选择 5 条预期回答长度不同的问题：短答案、约 100 字、约 500 字、约 2,000 字和结构化 JSON。每条同时记录：

- 请求发起时间 `t0`
- 首个增量片段时间 `t_first`
- 每个片段到达时间和长度
- 最后一个片段时间 `t_last`
- 页面结束时间 `t_done`
- 合并前原始片段与合并后最终文本

计算指标：

```text
首包延迟 = t_first - t0
流式持续时间 = t_last - t_first
端到端耗时 = t_done - t0
片段数 = 增量事件数量
增量总字符数 = 所有片段字符数之和
```

### 5.3 异常数据

- 空字符串、仅空格、仅换行的输入
- 超长输入、特殊符号、中文/英文/数字混合
- JSON、Markdown、代码块和多段列表
- 连续快速点击发送
- 发送过程中刷新页面
- 发送过程中关闭/恢复网络
- 模拟首包延迟、片段延迟、连接断开、HTTP 5xx、504
- 登录态过期后直接发送

## 6. 测试场景与用例矩阵

### 6.1 登录与登录态

| 用例 | 场景 | 主要步骤 | 通过标准 |
|---|---|---|---|
| CORE-LOGIN-001 | 正常登录 | 打开入口，输入测试账号密码并提交 | 登录成功；跳转到聊天或业务首页；无错误 Toast；登录态可被后续请求使用 |
| CORE-LOGIN-002 | 错误密码 | 输入错误密码提交 | 页面给出明确错误；不进入聊天页；不生成有效登录态 |
| CORE-LOGIN-003 | 登录态恢复 | 登录后关闭页面再打开聊天入口 | 无需重复登录或可按设计恢复；用户信息和会话可用 |
| CORE-LOGIN-004 | 登录态失效 | 清理/使 Cookie 或 Token 失效后访问聊天并发送 | 被引导重新登录；不出现“发送成功但无回答”假成功 |
| CORE-LOGIN-005 | 重复登录 | 连续提交两次登录 | 不产生重复会话；页面状态稳定；最终只有一个有效登录态 |

### 6.2 新建任务、发送和请求链路

| 用例 | 场景 | 主要步骤 | 主要判定 |
|---|---|---|---|
| CORE-SEND-001 | 新建任务后发送 | 新建会话，发送结构化输出问题 | 用户消息立即入列表；网络请求发起；助手占位状态出现；最终结束 |
| CORE-SEND-002 | 回车发送 | 输入问题后按 Enter | 只发送一次；与点击发送行为一致 |
| CORE-SEND-003 | 快速重复点击 | 在请求未完成时连续点击发送 | 不重复提交同一问题；按钮禁用或请求有幂等控制 |
| CORE-SEND-004 | 空输入 | 不输入内容直接发送 | 不发起无效请求；有明确前端提示 |
| CORE-SEND-005 | 请求失败 | 模拟接口 500/504 | 页面结束生成状态；显示可理解错误；记录失败状态并触发告警 |
| CORE-SEND-006 | 请求无响应 | 模拟请求一直 pending | 达到超时阈值后退出生成状态；页面可继续操作；告警包含请求信息 |

### 6.3 流式回答与“生成中”检测

| 用例 | 场景 | 主要步骤 | 主要判定 |
|---|---|---|---|
| CORE-STREAM-001 | 正常流式 | 发送约 500 字回答问题并监听响应 | 收到多个增量事件；首包和总耗时达标；片段可合并 |
| CORE-STREAM-002 | 首包超时 | 注入首包延迟 | 首包超时告警；页面不无限等待；留存网络 Trace |
| CORE-STREAM-003 | 中途断流 | 回答过程中断开连接 | 识别为异常结束；不能标记为正常完成；提供重试或明确失败提示 |
| CORE-STREAM-004 | 片段停滞 | 两个片段之间注入长间隔 | 触发流式停滞告警；生成状态最终可退出 |
| CORE-STREAM-005 | 无限生成 | 保持“生成中”或不返回结束标记 | 达到最大生成时长后失败；记录最后增量时间和页面截图 |
| CORE-STREAM-006 | 空完成 | 返回完成状态但正文为空 | 判定失败；不能仅依据 HTTP 200 判定成功 |
| CORE-STREAM-007 | 内容顺序 | 检查多片段拼接 | 无重复、倒序、丢片段、乱码；最终文本与原始片段一致 |

### 6.4 结果完整性、格式和会话恢复

| 用例 | 场景 | 主要步骤 | 主要判定 |
|---|---|---|---|
| CORE-RESULT-001 | 精确结果 | 发送精确计算问题 | 数值与预期一致；满足“只输出结果”约束 |
| CORE-RESULT-002 | JSON 结果 | 发送严格 JSON 问题 | 去除外层 Markdown 后仍可解析；字段和值正确 |
| CORE-RESULT-003 | 列表结果 | 发送三点列举问题 | 返回恰好三项；三项内容均存在 |
| CORE-RESULT-004 | 长回答完整性 | 发送长文本并统计字符数/末尾标志 | 末尾未截断；无“生成中”；字符数达到预期下限 |
| CORE-RESULT-005 | 保存会话 | 完成回答后刷新页面 | 用户问题和助手回答仍在；文本不变；状态为已完成 |
| CORE-RESULT-006 | 恢复历史会话 | 退出聊天后从历史列表重新打开 | 打开的是正确会话；多轮顺序和内容一致 |
| CORE-RESULT-007 | 发送中刷新 | 流式过程中刷新 | 页面不死锁；按产品设计恢复、失败或可重试；不能出现重复消息 |

## 7. 自动化实现方案

### 7.1 浏览器层

Playwright 每次运行执行以下步骤：

1. 读取环境变量中的站点地址和测试账号，不在代码和报告中写入密码。
2. 通过 `storageState` 复用登录态；失效时自动重新登录并记录登录耗时。
3. 监听 `request`、`response`、`requestfailed`、Console 和页面错误。
4. 发送带唯一标识的测试问题，防止从历史消息误判本次回答。
5. 同时记录按钮状态、输入框状态、生成中标识、消息数量和助手正文。
6. 监听流式响应，保存原始事件或响应片段，计算首包、片段数、最后片段和结束时间。
7. 每条用例失败时自动保存 PNG、Trace、网络摘要和结构化 JSON。
8. 测试结束生成 Markdown 汇总，并将失败项写入告警状态文件。

### 7.2 接口/网络层

API 文档用于确认可访问路由和基础 HTTP 状态；对未公开或流式协议不明确的接口，不直接猜测请求体，而通过浏览器网络监听记录真实请求。接口层重点采集：

- 请求 URL、方法、时间戳、状态码
- DNS/连接/首字节/总耗时（能够获取时）
- 失败类型、响应头、响应体摘要
- SSE/Fetch 流式片段数量、结束标记、连接关闭原因
- 关联的会话 ID、任务 ID 或请求 ID（脱敏后）

### 7.3 负载与故障注入

- k6：先做 1、5、10、30、50 并发阶梯，再做 10 分钟稳定性运行。
- Toxiproxy：分别模拟 2 秒、10 秒、30 秒延迟；断开连接；限制带宽；随机连接失败。
- 故障注入只在测试环境执行，运行前确认代理目标和恢复命令，运行后清理代理规则。

## 8. 阈值与通过标准

以下为第一版监控阈值，连续运行 3 个周期后根据基线调整：

| 指标 | 正常 | 告警/失败 |
|---|---|---|
| 登录成功率 | 100% | 任意一次关键账号登录失败即告警 |
| 页面入口 | HTTP 200 且关键元素出现 | 5xx、跳转错误、关键元素缺失 |
| 消息提交 | 发送后 5 秒内出现用户消息和请求 | 无请求、无用户消息或重复提交 |
| 首个流式片段 | ≤10 秒 | >10 秒告警；>30 秒失败 |
| 流式片段间隔 | ≤15 秒 | 单次间隔 >30 秒告警 |
| 最终完成 | ≤75 秒，页面退出生成状态 | >75 秒、一直“生成中”失败 |
| 返回正文 | 非空、完整、角色正确 | 空、截断、错位、乱码失败 |
| HTTP 错误 | 0 个 5xx/504 | 任意 5xx/504 告警 |
| 会话恢复 | 刷新/重开后内容 100% 一致 | 消息丢失、错会话或顺序变化 |
| 稳定性 | 10 分钟无失败、P95 在基线内 | 错误率 >0 或 P95 超基线 30% |

一次监控告警不立即判定为平台故障，可设置“连续 2 次失败触发故障告警、连续 2 次成功发送恢复通知”，但登录失败、5xx/504 和数据丢失可直接升级。

## 9. 监控运行频率

| 任务 | 频率 | 内容 |
|---|---|---|
| 核心探活 | 每 5 分钟 | 登录态、聊天入口、短问题、完成状态 |
| 标准流程 | 每 30 分钟 | 新建任务、发送、流式、格式校验、保存恢复 |
| 多轮会话 | 每 2 小时 | 3–5 轮上下文和刷新恢复 |
| 稳定性/负载 | 每日低峰期 | k6 阶梯、10 分钟稳定性，避免影响业务 |
| 故障演练 | 每周一次 | Toxiproxy 延迟、断流和 5xx/504 处理能力 |
| 完整回归 | 版本发布前 | 全部核心场景、异常场景和证据归档 |

## 10. 告警内容与整改闭环

告警必须包含：环境、用例 ID、发生时间、失败阶段、请求/会话脱敏标识、HTTP 状态、首包/总耗时、页面状态、错误摘要、证据目录和最近一次成功时间。

处理流程：

```text
定时执行 → 采集指标和证据 → 规则判定 → 告警通知 → 定位责任层
    ↑                                           ↓
复测通过 ← 修复并部署 ← 建立问题单 ← 保留失败现场和日志
```

问题单至少记录：复现步骤、影响范围、首次发现时间、相关请求 ID、前端/网关/服务端日志、根因、修复版本、验证用例和复测结果。禁止只写“测试失败”，必须能由他人按记录复现。

## 11. 测试执行顺序

### 阶段一：基线和协议识别

- 确认测试环境、账号、浏览器版本和时区。
- 访问 API 文档并保存路由清单。
- 使用 Playwright 记录一次真实登录、发送和流式请求。
- 确认消息 DOM、完成状态、请求 ID/任务 ID 和会话恢复方式。

### 阶段二：功能与数据正确性

- 执行登录、发送、流式、格式和恢复用例。
- 使用固定问题和预期校验，记录完整助手正文。
- 对每条回答保存原始片段、最终文本、耗时和截图。

### 阶段三：异常与故障注入

- 注入首包延迟、片段停滞、连接断开、接口 5xx/504。
- 验证页面退出“生成中”、错误提示、重试行为和告警。
- 检查异常后是否还能继续发送新消息。

### 阶段四：负载、稳定性和恢复

- 进行并发阶梯和 10 分钟稳定性测试。
- 测试多轮会话、刷新、重新打开和登录态失效恢复。
- 对失败项执行修复后复测，保留修复前后对比数据。

## 12. 交付物

每次运行必须输出：

- `summary.json`：用例、状态、耗时、错误类型、阈值判定
- `response-content.json`：问题与实际返回内容
- `network.json`：请求、响应、失败和流式事件摘要
- `screenshots/`：关键步骤和失败页面截图
- `traces/`：Playwright Trace，支持回放
- `report.md`：面向项目人员的测试报告
- `alert-state.json`：当前告警/恢复状态，防止重复告警

## 13. 本阶段验收标准

满足以下条件后，第二项目才算完成：

1. 登录、发送、流式、完成和保存恢复均有自动化用例。
2. 正常、边界、异常、长文本、多轮和格式化输出均有测试数据。
3. 能区分“请求成功但回答为空”“首包超时”“流式中断”“页面一直生成中”。
4. 每次失败都有可回放的截图、Trace、网络摘要和时间指标。
5. 5xx/504、超时和连续失败能够触发告警，恢复后能够发送恢复通知。
6. 修复后能够按原用例自动复测，并形成问题整改闭环。
7. 连续 3 个监控周期无关键失败，且稳定性测试达到阈值。

## 14. 当前已知风险与前置条件

- 测试环境曾出现“最近对话已达上限 100 条”，需要准备会话清理策略或专用测试账号，否则新建任务类用例会被环境容量阻塞。
- 当前 API 文档未完整描述流式请求体和响应事件，首轮实施应以浏览器真实网络记录为准，再固化接口级脚本。
- 如登录包含验证码、短信或人工确认，需要提供测试环境白名单、固定测试验证码或专用免验证码策略。
- 需要明确告警接收渠道和责任人；未配置渠道时，脚本只能生成本地告警状态，不能证明通知链路已验收。
- 需要服务端提供请求 ID、任务 ID和错误日志查询能力，才能把页面现象准确关联到后端根因。
