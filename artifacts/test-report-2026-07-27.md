## 2.1 使用这些工具的好处

### Playwright：验证真实用户操作和页面状态

Playwright 直接控制浏览器，可以验证普通接口测试无法覆盖的内容：

- 页面是否白屏；
- 输入框、发送按钮、完成/失败状态是否出现；
- 流式回答是否真正显示到页面；
- 刷新、切换会话后消息是否恢复；
- 两个独立浏览器上下文是否能同时工作；
- 失败时自动保存截图、视频和 Trace。

它的价值是把“接口返回 200”与“用户实际上能不能用”区分开。例如本次 S-100 中，页面接口并非全部报 5xx，但前端弹出了“最近对话已达上限 100 条”，只有浏览器自动化才能发现这个真实阻断。

### k6：快速、可重复地测量 HTTP 可用性和性能

k6 适合做站点探活和小流量接口测试，优点是：

- 可以固定请求次数、并发数和间隔；
- 自动统计平均值、P90、P95、错误率；
- 可设置阈值，让脚本自动判定通过或失败；
- 输出适合保存到监控和 CI 流程。

本次 AV-01 使用 k6 得到了 10 次请求、0% HTTP 错误率和 P95 37.33 ms，而不是凭一次浏览器打开结果判断“网站正常”。

### Toxiproxy：可控地模拟弱网、延迟、丢包和断网

真实网络波动难以稳定复现。Toxiproxy 可以把测试流量经过代理，再按场景注入：

- 300 ms 或 800 ms 延迟；
- 下载/上传限速；
- 5% 丢包；
- 短时断网；
- 超过前端最长重连时间的长断网。

这样可以重复验证流式重连、最终失败提示和恢复时间，而不是依赖偶然的家庭网络波动。该工具只应连接测试环境，不能直接对正式站点注入故障。

### Promptfoo：固定问题的批量答案和格式回归

稳定性测试只判断任务是否完成，不判断答案是否符合题目要求。Promptfoo 可以对固定题集执行统一断言，例如：

- JSON 是否能被解析；
- 是否只输出指定格式；
- 是否包含必需字段；
- 修改模型或提示词后，旧题集是否出现回归。

它适合做确定性的格式和规则检查，结果可以与 S-10/S-100 的耗时结果分开保存，避免把“回答内容不合要求”和“接口超时”混成一个指标。

### DeepEval：系统化评估开放式回答质量

开放式说明题不能只靠字符串相等判断。DeepEval 可以在提供评测标准或参考答案后评估：

- 相关性；
- 完整性；
- 事实一致性；
- 任务完成度；
- 回答是否包含不应出现的内容。

它需要明确的模型配置、评测数据或参考答案，不能在没有标准的情况下直接得出“回答质量好/坏”的结论。

### Windows 任务计划程序：把一次测试变成长期监控

任务计划程序是系统自带能力，可以按 5 分钟、30 分钟或每天的频率启动 Playwright/k6：

- 不需要人工每天执行命令；
- 可保存每次运行的时间和结果；
- 可在失败时触发报警脚本；
- 可在连续两次通过后发送恢复通知。

### 项目群机器人：让异常及时到达负责人

截图、Trace 和 k6 数字保存在本机，发现问题的人不一定是处理问题的人。群机器人可以把 P0/P1/P2 事件发送到项目群，并带上时间、环境、任务 ID、会话 ID、错误状态和证据路径，减少人工转述和遗漏。

### 为什么要组合使用

这些工具覆盖的是不同层次：

```text
浏览器真实体验       → Playwright
HTTP 可用性/性能      → k6
异常网络条件          → Toxiproxy
回答内容/格式         → Promptfoo、DeepEval
定时执行              → Windows 任务计划程序
异常通知              → 项目群机器人
```

单独使用 k6 不能发现白屏和消息错序；单独使用 Playwright 不能可靠统计 P95 和错误率；单独使用 Promptfoo 也不能证明任务创建和流式连接稳定。因此需要组合工具，并将可用性、性能、网络恢复和回答质量分别记录。

## 3. AV-01：站点可用性

执行命令：

```powershell
& 'C:\Program Files\k6\k6.exe' run `
  -e BASE_URL=http://192.168.0.112:23191 `
  -e ITERATIONS=10 `
  -e INTERVAL_SECONDS=1 `
  .\k6\site-smoke.js
```

脚本每次执行 `GET {BASE_URL}/`，分别检查：

1. HTTP 状态为 200；
2.响应正文不包含 `This deployment is temporarily paused`；
3. HTTP 状态不为 5xx；
4. `http_req_failed` 低于 5%；
5. P95 响应时间低于 5 秒。

结果：

- 请求数：10
- 检查项：30，全部通过
- HTTP 200：10/10
- 暂停提示：0
- 5xx：0
- HTTP 错误率：0%
- 平均响应时间：19.17 ms
- P95：37.33 ms

说明：本次为快速基线，间隔使用 1 秒；文档规定的正式低频检查应由 Windows 任务计划程序按 5 分钟周期运行。

## 4. S-10：10 道固定题

执行命令：

```powershell
$env:SCIENCE42_STORAGE_STATE="$PWD\playwright\.auth\science42.json"
npm run test:s10
```

测试方法：

1. 读取 `config/questions.json` 中的 10 道固定题；
2. 每道题点击“新建会话”；
3. 找到聊天输入框，填入题目并按 Enter；
4. 等待页面出现回答；
5. 记录首字时间、完成时间、HTTP 状态和页面状态；
6. 单题最长等待 75 秒；
7. 失败时保留截图、视频和 Trace。

通过标准：10/10 有明确回答，没有白屏、5xx 或无限“生成中”。

结果：10/10 通过。后续修正了测试环境的“新建会话”定位器，使其点击实际新增按钮 `svg path#add_svg__a`，避免误用旧会话。

## 5. S-30A：30 道任务串行稳定性

执行命令：

```powershell
npx playwright test playwright/s10.spec.mjs `
  --project=chromium `
  --repeat-each=3 `
  --workers=1
```

参数含义：

- `--repeat-each=3`：同一固定题集执行 3 轮；
- `--workers=1`：确保轮次串行，不产生额外并发；
- 每轮 10 题，每题新建会话；
- 不设置重试，原始失败不会被重试覆盖。

结果：3/3 轮通过，共 30/30 任务完成。

## 8. S-100：100 次任务

执行命令：

```powershell
npx playwright test playwright/s10.spec.mjs `
  --project=chromium `
  --repeat-each=10 `
  --workers=1
```

执行方法符合文档：10 轮、单 worker、每题新建会话、不启用重试。

实际结果：

- 第 1～5 轮：50/50 任务完成；
- 第 6 轮开始：平台无法新建会话；
- 页面提示：`最近对话已达上限 100 条，请先删除后再新建`；
- 因此 S-100 完成度为 50/100，不能判定通过。

该失败不是脚本超时，而是平台达到最近对话上限后的业务阻断。未自动删除历史会话，避免破坏测试数据。

## 9. 发现的问题

### TEST-001：最近对话达到 100 条后无法新建会话

现象：新建会话时出现“最近对话已达上限 100 条，请先删除后再新建”。

影响：

- S-100 后 50 个任务无法执行；
- 长期监控、批量回归和连续使用会被硬阻断；
- 用户只能手工删除历史会话后继续使用。

等级：P1。若正式环境稳定复现并导致聊天不可用，可升级为 P0。

证据：

```text
test-results/s10-S-10-fixed-questions-one-new-conversation-per-task-chromium-repeat5/test-failed-1.png
test-results/s10-S-10-fixed-questions-one-new-conversation-per-task-chromium-repeat5/trace.zip
```

整改：

1. 增加分页、归档或自动清理策略，不把 100 条作为硬阻断；
2. 新建失败返回稳定错误码和明确操作提示；
3. 修复后先重跑 S-10，再继续 S-100；
4. 修复验证期间不通过删除历史记录来制造“通过”。

## 13. 第二阶段：平台核心流程监控实现

针对新的第二个项目目标，已新增：

```text
monitor/core-flow-monitor.mjs
monitor/run-core-monitor.ps1
```

执行命令：

```powershell
$env:SCIENCE42_MONITOR_URL='http://192.168.0.112:23191'
$env:SCIENCE42_STORAGE_STATE="$PWD\playwright\.auth\science42.json"
$env:MAX_TASK_MS='75000'
npm run monitor:core
```

监控步骤：

1. 打开测试环境入口；
2. 检查登录状态，发现登录框即判定登录失败；
3. 进入聊天页，兼容案例页的“返回聊天”路由；
4. 检查输入框是否可见；
5. 发送带时间戳的唯一监控问题；
6. 等待本次问题对应的流式回答，避免误读旧会话内容；
7. 判断是否在 75 秒内得到完成结果；
8. 保存 `result.json`、页面截图和 Trace；
9. 连续 2 次失败发送 P1 告警；
10. 告警后连续 2 次成功发送恢复通知。

本次监控试跑结果：

- 状态：失败；
- 原因：Playwright 保存的登录状态已失效，页面重新出现登录框和滑块验证码；
- 证据目录：`artifacts/core-monitor/2026-07-27T08-21-35-411Z/`；
- 群报警：未发送，因为尚未配置 `ALERT_WEBHOOK_URL`。

这说明核心流程监控脚本可以识别登录失效，但长期运行还需要平台提供以下之一：

- 可续期的监控 Token；
- 不需要人工滑块的专用监控账号；
- 后端提供服务账号登录或健康检查接口。

不建议把人工验证码账号直接用于每 30 分钟的定时监控。
